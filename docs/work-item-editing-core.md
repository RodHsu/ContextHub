# Work item editing core — staged source

The source foundation adds the Application command/aggregate core and PostgreSQL store. The adapter stage routes ordinary existing REST/MCP WorkItem updates, archive/restore, checklist completion and governance-exclusion relationship edits through that core. The actual WorkItem page now uses the HTTP edit/recovery protocol and draft controller for metadata, lifecycle and checklist completion edits. WorkItem proposal archive/restore now uses the separate committed-dispatch and exact-receipt recovery protocol described in [proposal recovery](work-item-proposal-recovery.md). Governance immutable preconditions, Memory CAS and structural checklist editing remain separate dependencies. Do not deploy these stages alone or infer end-to-end CAS from the additional read revision. All writer adapters, public contract/host acceptance and database acceptance remain required gates before rollout.

## Intent and original version

WorkItemEditCommand requires an explicit regular project, target, positive original-read revision, bounded request identity, operation and typed patch. Missing original revision rejects; the server does not fill it with a current version. The production read DTO preserves an omitted revision as unknown/null; only an actual mapped row supplies the database baseline. Migration baseline1 is not reconstructed history.

The normalized WorkItemEditIntent/v2 fingerprint binds canonical project identity, work item, original revision, operation, field presence, leaf identities/order and effective values, including the privileged governance-exclusion relationship change. It supersedes the unpublished foundation's v1 hash shape; no v1 receipt conversion or backward-compatible recovery is claimed. RequestId is a separate scoped ledger key. DueAt has explicit Keep/Clear/Set intent. The same scoped key with a different fingerprint conflicts. Read-only receipt recovery requires the pending intent's original fingerprint/version; it cannot mistake an old result for a different reused-key intent.

## Adapter contract and recovery

Ordinary legacy writers without a positive original revision reject with MissingReadVersion. Authorized project lookup does not supply a current revision on the client's behalf. Existing scalar MCP wrappers accept expectedRevision/requestId and dispatch typed Application requests. REST updates distinguish omitted dueAt (Keep), explicit null (Clear) and a date (Set); typed patches cannot be mixed with flat update fields. Completed uncheck still requires an explicit Reopen edit and its own committed history.

POST `/api/work-items/{id}/edits` accepts the canonical command. GET `/api/work-items/{id}/edit-receipts` takes projectId, requestId, expectedRequestHash and hashVersion; a null/404 result is not proof the original edit never arrived. Current tenant/owner/service-actor/project authority and the original fingerprint are checked before returning the original result. Errors expose known safe conflict codes, opaque forbidden/not-found responses or a generic unknown-outcome response. A trace identifier in an error is not a replacement edit identity. The caller must retain its original key/hash/version before submission.

The privileged exclusion operation retains existing MemoryWrite, admin and GovernanceTrackerManage checks, a same-actor/tenant review snapshot containing the project, and the original security audit. The store saves the relationship, history, audit, receipt and outbox in its one owned transaction. This does not change or complete the separate governance executor's immutable-snapshot integration.

The draft controller binds identity+project+target, preserves drafts and original revision on 409, and requires explicit comparison acceptance before a new intent. Late read/write/recovery responses are ignored after scope changes or disposal. Cancellation, malformed success or uncertain transport leaves the exact request pending; no automatic replay/new key/latest-version fill occurs. Only non-secret recovery metadata can be captured. The controller is in memory: leaving/reloading the page or restarting can lose custody. Durable checkpoint storage remains unimplemented.

The actual page derives its UI binding key from the authenticated Dashboard principal, not a credential or a client-supplied authorization claim. Pending/new identities clear private view state; late list/authentication results cannot repopulate an old identity. Rendered form/actions also capture their original scope generation so an old event cannot edit or submit a different scope after rebinding. The existing named legacy Dashboard cookie has its own distinct binding kind; partial tenant identities fail closed. Server Application authority remains mandatory on every read/edit/recovery.

A same-project list refresh preserves the selected editor and its original revision/draft, even when the selected item falls outside the bounded list. List absence is not proof of lost authority. The user can compare a separately authorized detail read and explicitly adopt it. An older original receipt cannot downgrade a newer revision already present in the list. Ordinary metadata drafts block unrelated lifecycle/checklist actions until saved; after adopting an archived conflicting read, explicit Restore sends only its lifecycle intent and retains the draft for a later save. Completed checkboxes require explicit Reopen before unchecking. No progress baseline or earned evidence is recalculated.

The managed component tests dispatch real Blazor render-tree events through the actual panel/page and production controller/client contracts. Synthetic API responses test wiring, races and presentation; they do not prove browser DOM behavior, PostgreSQL concurrency, committed transactions or Production acceptance. Structural checklist add/text/remove/reorder UI and durable host custody remain separate follow-up work even though the core operations exist.

### Tool-surface review

`project_work_item_edit_receipt_get` is a distinct read-only recovery query on the general backend and restricted gateway. Current WorkItem detail/list cannot answer whether a particular request committed, and adding optional historical-ledger modes to those queries would conflate current state with original results. The tool uses existing MemoryRead plus current resource authority and the exact actor-scoped request fingerprint; it grants no new role, mutation, delete, replay or global ledger capability. Both surfaces share the same Application use case and SDK input schema. The general catalog advances to 2026-10-26-v11; the dedicated Scheduled Governance four-tool catalog/schema and acceptance gates are unchanged. Host publication/reconnect/schema acceptance remain unexecuted release gates.

## Aggregate and commit

The production aggregate helper validates a candidate before changing tracked objects. It preserves stable child identities, advances revision/time once per real logical edit and retains no-op revision/time. Completed uncheck or a new incomplete leaf requires explicit reopen. Reopen changes Completed to InProgress; before/after history retains the previous completion status/time. Valid metadata/text/reorder/removal do not automatically reopen a completed work item. No earned units or progress baseline is recalculated here.

The PostgreSQL store uses a fresh context and one ReadCommitted transaction, with a transaction-scoped advisory lock keyed by tenant+work item. A query after a contended lock sees a fresh snapshot, so a duplicate can find the first committed receipt. Scope is tenant plus owner or existing service-actor scope and canonical project; the Application service checks current actor scopes/project before dispatch. The store checks the receipt fingerprint before comparing the original revision. Parent revision is an EF concurrency token; new child IDs are explicitly Added/INSERT rather than left to relationship discovery, and removed children are explicitly deleted in the same transaction.

A changed aggregate, immutable before/after history, immutable scoped receipt and transactional outbox event are saved/committed together. A no-op persists only its receipt. An apply result is returned after this store's commit completes. Cancellation/transport failure at commit is unknown until exact same-request recovery; it does not cause automatic replay. Receipt result is the original committed result, not current-state or signed-proof evidence.

Current ambient transactions are explicitly rejected by this foundation. The WorkItem proposal adapter now uses explicit separate commit owners: a durable one-shot dispatch marker, the core edit transaction, then receipt-bound proposal finalization. This is a recoverable workflow with a documented pre-dispatch failure window, not an atomic proposal-and-edit transaction. Governance composition still requires immutable original versions and an explicit commit/result protocol; nesting this store and calling a staged receipt committed remains incorrect.

## Migration and validation boundaries

Embedded migration059 is additive: positive parent revision, scoped unique receipt key, unique work-item revision history, step/identity/hash checks and append-only history/receipt triggers. Apply it only through the normal approved migration path. EnsureCreated/model metadata does not install the SQL append-only triggers and is not equivalent acceptance. The source change has not executed this migration or any database query.

Pure-helper, actor-dispatch, actual EF model/query translation and change-tracker tests can run without a connection. They do not establish PostgreSQL advisory-lock behavior, uniqueness/collision isolation, rollback/commit cancellation or trigger enforcement. Real database transaction/concurrency/restart evidence remains required and unexecuted under the current resource gate.

## Rollout and rollback

First finish all writer adapters and legacy rejection/read-reload flow, then verify schemas/host publication, migration readiness and actual database invariants. Existing immutable governance snapshot/execute/Natural gates are not weakened; old snapshots without an original version cannot be upgraded by reading latest. Source endpoint/tool registration does not establish deployment or host publication, and these incomplete stages are not ready for release.

If rollout is incomplete, keep versioned edit entry points unavailable. Rollback preserves additive revision/history/receipt data and uses compatible writers or read-only editing; it must not drop evidence or return to blind overwrites after guarded edits have occurred. A destructive down migration is deliberately not supplied.
